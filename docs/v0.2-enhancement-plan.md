# v0.2 enhancement plan

Status: first evidence/brief slice implemented on 9 September 2026; later slices remain proposed. See README for exact scope and limitations.

Baseline: GitHub main `57dea9d68943de5e85c4345795071e9bb9f1c4f5`, designated `v0.1`. Work branch: `v0.2`. Git release names are independent of Sites version numbers and the existing package.json version.

## Outcome

Turn the assessment demonstration into an evidence-led case workbench: an underwriter can see what is known, what conflicts, which policy applies, why a recommendation follows, and exactly what would unblock the case. A customer provides only the information still needed. Improving measured decision quality is a separate objective from making the UI more convincing.

## Findings from the current implementation

- `dist/engine.js` contains six scripted profiles. Mock ML largely follows referral rules; it is not a trained predictor. Additional numerical attributes do not establish predictive accuracy.
- `server.py::extract` returns narrative findings with document/page/quote references. There is no typed longitudinal observation model, deterministic unit normalization, or field-level contradiction resolution.
- `ml_screen` validates response types and uploaded-document hashes, but calibration and completeness remain adapter assertions. Hash identity does not establish clinical sufficiency, freshness or product eligibility.
- `reasoning_errors` checks citation IDs and requires an internal citation for proposed terms. It does not establish that the cited clause supports each proposed term, is current, or applies to the product and jurisdiction.
- Assessment orchestration and case state live in the browser. The local runner exposes individual steps without authoritative persisted case transitions. Cancellation does not necessarily terminate inference.
- Current confidence, rule traces and reviewer marks are helpful, but there is no measured holdout evaluation, case queue, controlled feedback dataset, or customer evidence-request journey.
- The current life and medical workflows share broad controls. Their risk objectives, product terms and permitted actions need separate policy packs.

## Ordered implementation slices

| Order | Deliverable | User benefit | Acceptance criteria |
|---|---|---|---|
| 1 | Structured evidence and decision brief | Check facts quickly before deciding | Typed observations; source page/quote; declarations versus verified findings; unknown/conflicting states; unresolved material conflicts block STP |
| 2 | Baseline evaluation harness | Demonstrate whether an enhancement actually helps | Frozen fixtures; separate extraction/retrieval/routing metrics; baseline comparison; repeated local-model runs; no fabricated metrics |
| 3 | Evidence requests and case workflow | Reduce repeated questions and lost work | Missing items tied to requirements; consolidated customer request; upload/review/resubmit; changed evidence invalidates dependent results |
| 4 | Product policy packs and decision rationale | Explain which approved guidance supports a decision | Effective dates, jurisdiction, product and authority checked; clause-level support; draft/approve/activate history; rollback and replay |
| 5 | Model assurance and performance | Make fast processing dependable and measurable | Versioned validation manifest; calibrated threshold selection; OOD/abstention; bounded concurrency; latency and failure telemetry |

Build slice 1 first, introducing its labelled fixtures at the same time; freeze the baseline in slice 2 before claiming improvement. Keep mock and real adapters on the same schemas. Preserve the existing UI stack for these slices.

## 1. Evidence that assists the underwriter

Use a three-part case view: compact decision brief, evidence workspace, and persistent next-action panel. Keep the technical execution trace in an expandable section. Put blocking issues above reassuring indicators.

The brief should show application/product/version, proposed outcome, decisive facts, counter-evidence, missing requirements, applicable clauses, referral reason, and permissible next actions. Each material statement links to evidence; distinguish observed fact, applicant declaration, calculated value and model interpretation.

Proposed observation contract:

```json
{
  "id": "OBS-001",
  "case_id": "CASE-DEMO-01",
  "field": "hba1c",
  "raw_value": "6.8",
  "raw_unit": "%",
  "normalized_value": 6.8,
  "normalized_unit": "%",
  "observed_at": "2026-06-01",
  "source": {"document_id": "DOC-1", "sha256": "<document hash>", "page": 2, "quote": "<source excerpt>"},
  "status": "extracted_unverified",
  "extractor_version": "<model and prompt version>",
  "review": null
}
```

Retain original values. Represent absent dates/units as null; never silently infer them. Record corrections as new versions with actor, reason and timestamp. Bounding boxes are optional only where supported. A normal laboratory range is not an insurer's acceptance threshold.

Add medical chronology: diagnosis onset, treatment changes, medication/dose, admissions, investigations, pending tests, trends and follow-up. Keep negated, suspected, historical and confirmed conditions distinct. Record patient identity consistency, report author/date, legibility, duplicate reports, provenance and coverage gaps. Do not resolve inconsistent reports by choosing the latest without review.

Life-specific context: purpose of cover, existing/pending cover, verified income evidence, term, financial justification and reinsurance authority. Medical-specific context: plan and benefit schedule, declared history, ongoing treatment, pending investigations and policy-supported terms. Use occupation duties and hazards where relevant, rather than stereotypes from occupation names. Collect sensitive attributes only where justified by the applicable approved policy; availability alone is not a reason to use them.

Add comparison of eligible options: standard, referral, further evidence, postponement, and policy-supported revised terms. Explain required evidence and authority for each. What-if edits must be isolated simulations, never overwrite observed evidence or imply causal predictions. Similar historical cases may aid review only with comparable product/policy versions and documented differences; prior decisions are not ground truth.

## 2. Accuracy evaluation

Start with at least 30 deliberately varied synthetic fixture cases, then obtain an independently adjudicated, de-identified historical holdout for meaningful validation. Synthetic tests establish behaviour, not mortality or claims accuracy. Include standard life/medical, missing pages, illegible numbers, unit mismatch, contradictory declarations, old reports, wrong-person documents, negation, duplicate documents, prompt injection, out-of-distribution cases, ML timeouts, stale policy and unsupported proposed terms.

Split by applicant and time; prevent document duplicates and future information from leaking across train/tune/test. Label required facts, evidence spans, applicable clauses, permissible routes and prohibited outputs. Two underwriters adjudicate disputed decisions. Record policy version and label uncertainty.

Measure separately:

- Extraction: field precision/recall, exact numeric-plus-unit accuracy, material omission rate, source-span support.
- Retrieval: applicable-clause recall, wrong-version/jurisdiction retrieval and unsupported citation rates.
- Routing: false-standard acceptance among nonstandard cases, error rate among autoaccepted cases, referral recall, STP coverage and abstention rate. Show denominators and confidence intervals.
- Model assurance: calibration/Brier score against the stated target, subgroup and product breakdowns, OOD detection. Decision agreement is separate from long-term mortality/claims outcomes.
- Experience: time to decision, active underwriter minutes, repeat evidence requests, customer completion and abandonment, p50/p95 latency.

Compare v0.1 and v0.2 on identical frozen fixtures, then ablate normalization, retrieval and verification to identify useful changes. Repeat stochastic trials and capture model, prompt, rule, corpus and dataset versions. No aggregate trust score or claimed percentage uplift without measured results.

Proposed demo release gates: all deterministic blocking scenarios pass, every material recommendation has inspectable support, and no observed false STP acceptance on the safety fixtures. This is not proof of production safety. Production risk tolerances and statistical sample sizes require actuarial and underwriting agreement before evaluation.

## 3. Streamlined customer and underwriter journeys

Customer: select product → answer adaptive declarations → see a tailored document checklist → upload with quality checks → confirm extracted details → view plain-language progress → receive one consolidated missing-information request → resubmit → receive reviewed outcome and correction/review route. Do not expose raw model risk scores or internal fraud speculation to applicants. Messages remain drafts until an authorized user sends them.

Underwriter: queue by actionable status → inspect decision brief → review flagged evidence beside its source → request only missing items or correct extraction → reassess affected steps → compare permitted outcomes → record decision and explanation. Include owner, due date, waiting-on party and reassignment. Avoid promising completion times before they are measured.

Add a case state machine: draft, submitted, processing, needs_evidence, ready_for_review, decided, reopened. Evidence changes produce a new assessment revision. An old response cannot replace a newer assessment. Rules/instructions changes show an impact diff and invalidate the affected result.

For the static demo, simulate case queues and customer/underwriter views using fictional fixtures with clear session-only state. For local testing, introduce a server-owned case store and job orchestration before durable real-data workflows. Do not store medical documents in browser localStorage. Authentication, authorization, retention, encryption and immutable audit are prerequisites for shared operational use.

## 4. Rules, retrieval and reasoning

Introduce product/jurisdiction/version/effective-date policy packs. Extend typed rules to bounded AND/OR groups with explicit missing-data semantics and precedence. Add conflict detection, draft comparison, historical replay, approval roles and rollback. Natural-language rule drafting may generate a proposed typed rule; it cannot activate it. Separate response-style preferences from substantive assessment instructions so a formatting preference need not trigger costly reasoning.

Use deterministic policy lookup for exact requirements, lexical/vector retrieval for passages, and graph/OKF adapters for relationships. Filter by applicability before ranking. Internal approved policy governs insurance terms; external references provide attributed context. Internet search uses redacted general queries, never applicant identifiers, and cannot override policy. Record source version, retrieval date and clause ID.

Add claim-to-evidence links and verification for proposed terms, units, dates and contradictions. An optional second model may flag unsupported statements but is not an independent guarantee. Keep the reasoning workflow bounded: extract → normalize/check → retrieve → propose → verify → one repair or refer. Preserve concise explanations rather than exposing hidden chain-of-thought.

## 5. Reliable fast path and local performance

Require an applicable approved model manifest: target definition, feature schema, model/calibration versions, validation cohort/date, approved product scope and thresholds. Reject missing or incompatible manifests for real STP. Verify evidence freshness and requirement coverage independently of the ML probability. Use a structured-data fast path only when evidence is already verified; route newly uploaded evidence through document processing as needed.

Move authoritative routing to the runner; preserve frontend simulation in mock mode. Use assessment IDs, idempotency, stage checkpoints, server-side cancellation status and stale-response rejection. Cache document extraction by content hash plus extractor configuration, and invalidate policy-dependent results on policy changes. Bound page processing, timeouts, retries, concurrent model calls and total token budgets. Support separate extraction/reasoning endpoint configurations without assuming extra GPU capacity. Benchmark real local endpoints before selecting models or concurrency.

Keep traces of stage duration, outcome, version and error code, with medical content excluded by default. Add a feedback queue for reviewer corrections; adjudicate before adding them to a training dataset. Never retrain automatically from every override.

## Files and first implementation boundary

Slice 1: add shared observation schema, synthetic longitudinal fixtures and evidence normalization/conflict modules; extend `server.py` extraction validation; add source-linked brief and evidence workspace to `dist/app.js`; add focused fixture tests. Do not refactor the entire app or introduce a new framework first.

Slice 2: add `evals/` datasets, expected outcomes, runner and comparison report. Slice 3 introduces case state and request schemas. Slices 4–5 then build on those validated contracts.

The initial planning commit changed no application behaviour. The subsequent first slice adds the evidence brief and observation checks; it does not deploy the hosted Site.

## Research informing the proposed design

Munich Re describes combining underwriting expertise, EHRs and AI, with referral when required data cannot be found. This supports prioritizing evidence completeness and reviewed policy application, rather than trusting an LLM-only conclusion. It is a life-underwriting example; extending the pattern to medical insurance here is a design proposal, not evidence of equivalent validation. [Munich Re, 20 November 2025](https://www.munichre.com/us-life/en/insights/future-of-risk/beyond-the-model-building-assessments-risk-tools-for-EHRs-in-alitheia.html).

Anthropic recommends evaluations that capture outcomes and trajectories, with multiple trials for variable agent behaviour. The proposed baseline and versioned replay apply that general engineering approach to this demo; they do not establish insurance-specific performance. [Anthropic, 9 January 2026](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents).

Open dependencies: approved SG/MY product manuals and permitted attributes, clinician/actuarial adjudication, historical dataset access and outcome definitions, external-data permissions, and chosen local API endpoints. No jurisdictional compliance claim or actuarial threshold is supplied by this plan.
